Catching mule rings before the money leaves

The architecture as built, the production design on AWS, and the one constraint that shapes both: a mule account forwards victim money within minutes, so detection that runs the next morning finds an empty account.

The constraint: a race against the forward

Everything below follows from this timeline. A batch system can find the whole ring, but only after the money is gone. A streaming system can stop the first forward, but only if the features it needs (how fast this account usually moves money, who it pays, whether its phone is shared) are already computed. So the production design runs two paths: a fast one that scores every credit, and a slow one that builds the graph and the model the fast path depends on.

As built: the portfolio system

Everything runs on one machine with free tools. Each box below is a real module in the repository. The batch path is complete; the streaming path is the production step.

Production design on AWS

The same components split into three paths that run at different speeds. The real-time path decides on each credit in seconds. The batch path builds the lake, the graph and the model every few hours. The case path is where people and the AI investigator work in minutes. Everything runs in the Mumbai region because RBI requires payment data to be stored in India.

Decisions and trade-offs

Two paths, one feature definition

Fast and slow paths compute the same features in different engines, which risks training/serving skew. Each feature is defined once and tested on both engines against the same replayed day.

Debit-freeze, not full freeze

A false positive on a student's account is a real cost. The fast path only blocks outgoing money and asks for step-up authentication. A full freeze needs an analyst.

Weak labels, closed loop

Complaints name only about 40% of mules, and only the first hop. The model trains on them, graph expansion finds the rest, and analyst decisions become the next training labels.

Group splits by ring

Accounts in one ring look alike. Random splits leak and inflate scores, so validation holds out whole rings.

The LLM drafts, a person decides

The investigator can only read masked gold tables, every tool call is logged, and its STR is a draft that an analyst approves before filing.

Idempotent alerts

Streams retry. Every alert carries a deterministic id (account and credit id), so a replay never opens a duplicate case or applies a second hold.

Deploying the demo on the AWS free plan

The full production design is not free. A credible portfolio slice is: the S3 lake with the gold tables as parquet, Athena for the investigator's read-only queries, a Lambda that rebuilds and scores nightly, DynamoDB for case decisions, and the console as a static page. Lambda and DynamoDB stay within the always-free limits at this size; S3 and Athena cost a few rupees from the free-plan credits. Set an AWS Budgets alert before deploying.
